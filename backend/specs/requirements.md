# Спецификация требований — Бэкенд парсера конкурсных списков

## 1. Цель проекта

Бэкенд-сервис, который периодически собирает конкурсные списки абитуриентов с сайтов вузов
(первый вуз — СПбПУ), сохраняет их в PostgreSQL с историей изменений (снимками) и
предоставляет API для управления парсером. Данные затем использует фронтенд-приложение
для построения гистограмм распределения баллов с фильтрацией по вузу, направлению, приоритету.

## 2. Функциональные требования

### FR-1. Парсинг списков СПбПУ

**Описание:** Система собирает списки подавших заявления со страницы
`https://my.spbstu.ru/home/abit/list-applicants/bachelor` для направлений,
указанных в `config.json` (форма обучения «Очная», условия «Бюджетная основа»).

**Критерии приёмки:**
- [ ] Парсер получает список направлений (внутренние id и названия) с сайта СПбПУ.
- [ ] Парсер сопоставляет направления из `config.json` (код вида «09.03.04») с внутренними id сайта.
- [ ] Для каждого направления собираются все строки таблицы: уникальный код поступающего,
      БВИ, сумма конкурсных баллов, сумма баллов за ВИ, баллы за ИД (общие и целевые),
      преимущественное право, приоритет, согласие на зачисление, статус рассмотрения.
- [ ] Собирается сводка по направлению: количество мест, количество заявлений,
      количество согласий, время формирования списка.
- [ ] Между запросами по направлениям выдерживается пауза 1–2 секунды.

### FR-2. Хранение данных с историей

**Описание:** Каждый запуск парсера создаёт снимок (snapshot). Все записи абитуриентов
привязаны к снимку — это позволяет видеть динамику списков по дням.

**Критерии приёмки:**
- [ ] Каждый запуск создаёт запись `parse_snapshots` со статусом (`success` / `failed` / `partial`).
- [ ] Записи абитуриентов сохраняются массово (bulk insert) в транзакции.
- [ ] При падении парсинга одного направления остальные направления не теряются
      (статус снимка `partial`).

### FR-3. Конфигурация вузов и направлений

**Описание:** Список вузов и направлений задаётся вручную в файле `config.json`.

**Критерии приёмки:**
- [ ] `config.json` валидируется Pydantic-схемой при старте приложения.
- [ ] Добавление нового направления не требует изменения кода.
- [ ] Некорректный конфиг даёт понятную ошибку с указанием поля.

### FR-4. API управления парсером

**Критерии приёмки:**
- [ ] `POST /api/v1/parser/start` — ручной запуск парсинга (всех или одного направления).
- [ ] `GET /api/v1/parser/status` — статус последнего запуска и краткие логи.
- [ ] `GET /api/v1/config` — просмотр текущей конфигурации.

### FR-5. Периодический запуск

**Критерии приёмки:**
- [ ] Парсинг запускается автоматически каждые N часов (N — из `config.json`).
- [ ] Одновременно выполняется не более одного парсинга (защита от наложения запусков).

## 3. Нефункциональные требования

- **NFR-1. Расширяемость:** базовый абстрактный класс парсера; новый вуз = новый класс-наследник.
- **NFR-2. Диагностика:** при ошибке парсинга сохраняется скриншот страницы и текст ошибки.
- **NFR-3. Устойчивость к WAF:** все запросы содержат заголовки `Referer` и `User-Agent`
  (без `Referer` сервер СПбПУ отвечает ошибкой «upstream» — проверено).
- **NFR-4. Среда:** разработка под Windows; Python 3.11+; асинхронный стек
  (FastAPI, SQLAlchemy async, Playwright async).
- **NFR-5. Простота:** файлы небольшие (< 200 строк), модульная структура, понятные имена.

## 4. Вне области (out of scope)

- Фронтенд-визуализация (отдельное приложение, уже есть прототип).
- Парсеры других вузов (только заготовка в виде базового класса).
- Авторизация в API управления (сервис работает локально).
